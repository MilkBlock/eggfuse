# GPU 上可接续的因子化 Cell 状态

这是一个**实际在 Metal GPU 上运行的独立关系计算原型**。它把有限的
正关系查询片段编译成 FP16 矩阵乘法、FP32 累加、阈值、逐元素乘法和
局部等价类合并。包含动态输入绑定、两条分支的相关汇合，以及中途 union。
不是 EggFuse runtime 接管，也不是 native egglog 的端到端加速。

## 可复现入口

需要 Apple silicon、macOS 15+ 和带 Swift/Metal 的 Xcode 工具链。
Python 仅使用标准库。使用新的输出目录：

```sh
python3 benchmarks/cell-gpu-factors/run.py --output out/cell-gpu-factors/new --repeats 9
```

该命令生成数据和矩阵执行计划、编译 Swift host、运行 GPU，再与独立
CPU 集合 oracle 比较。构建、原始张量和逐阶段输出都留在忽略的 `out/`。
只提交可复现源和 [文本结果](results.json)。未修改当前 CPU/compiler，
没有重复跑 Cargo 或 sum-bits/Raytrace 性能测试。

## 目标与已有工作的关系

历史 `resident_ridge` 原型已经能常驻 GPU，执行矩阵评分、精确 guard、
slot map 和坐标更新。它的准入不包括跨 context join 和 inherited-class
merge。本实验单独验证这两类操作的一小部分数值表达，不复用其受限 ABI
冒充完整支持，也没有用回归分数授权效果。

当前分支的 [semijoin 实验](../../docs/SEMIJOIN.md)表明，减少访问次数
可能被维护、分派和数据搬运成本抵消。这里直接比较可接续状态的三种
执行布局，并把 union、临时空间、提交等待和最终读回列出来。

没有从真实 catalog 自动学习或提取新 Cell；`run.py` 是针对下述已知
查询 DAG 的小型离线编译器。相对当前 EggFuse 分支的吞吐变化未测。

## 实际计算了什么

每批实例有固定、稳定的端口编号。数据如下：

```
P(x,u)                  x 连接到边界端口 u
Q(v,z)                  边界端口 v 连接到 z
Eq(u,v)                 当前局部等价关系
S(z,y), T(z,y), W(y,o)   另外三组运行时关系

M(x,z)  := exists u,v. P(x,u) AND Eq(u,v) AND Q(v,z)
A(x,y)  := exists z. M(x,z) AND S(z,y)
B(x,y)  := exists z. M(x,z) AND T(z,y)
D(x,y)  := A(x,y) AND B(x,y)
F(x,o)  := exists y. D(x,y) AND W(y,o)
```

A 和 B 中的 z 分别量化；它们通过共同的 x、y 汇合，不能要求两条
分支使用同一个中间见证。生成的数据包含每行多个端口、空成员、不同
分支的不同见证。检查会刻意运行一个错误的“只合并同列因子”实现，
要求它在每个案例中被 oracle 区分，避免相关性测试退化。

每个 job 先计算一次 F，随后在 GPU 上执行四个 union 请求，再计算
第二次 F。请求包含通过已合并端口继续合并、重复合并及自身合并。
不同 batch 有不同事件。全部在**一个 command buffer** 中完成，没有
CPU 读取中间状态来选择下一步。

这个观察边界是有限正关系片段自己的边界，不模拟任意 egglog Run。
GPU 修改的是真实局部 parent 数组及关系因子，不是全局 egglog union
或构造子提交。最终关系位表示存在性，不表示已提交图突变。

## 数值表示和三种执行计划

令 H(t) 为 t>0 时取 1 的阈值。U 的行为 x、列为局部等价类，V 的行为
z、列为同一组类。逻辑匹配关系是 `M = H(U V^T)`。

合并类 a、b 时，GPU 对 U 和 V 同时执行：

```
column[a] = max(column[a], column[b])
column[b] = 0
parent[b] = a
```

这自然包含两个新交叉组合。父指针查找使用精确 u32；不用浮点近似 ID。
列的容量保持固定，不压实；因此后续成本仍按原 rank 支付，不能把
已清空列计为实际省下的矩阵运算。

三种计划共用同一个 GPU 矩阵 kernel、输入、union 和输出：

- `dense`：生成完整 M，分别连接 S/T，逐元素交汇，连接 W。
- `factor`：先算 `VS=H(S^T V)`、`VT=H(T^T V)`。交汇的精确因子为
  `L2[x,(i,j)]=U[x,i]U[x,j]` 和
  `R2[y,(i,j)]=VS[y,i]VT[y,j]`。继续计算 `R3=H(W^T R2)`，最后才
  生成 `F=H(L2 R3^T)`。M、A、B、D 都不展开。
- `cut`：先以因子完成两条连接，再生成 A/B；在交汇处改用展开表示。

**交汇可能把 rank 从 r 增到 r²。** 这里实际支付了全部 r² 存储和计算，
没有假设相关性消失，也没有用近似低秩分解。小编译器按逻辑运算数
选择计划，仅输出其选择作诊断，不隐藏其他计划的结果。该简化成本模型
没有 kernel 延迟项，因此会选错小案例，尚不能用于生产准入。

所有 GEMM 输入都是精确的 FP16 0/1，每次输出都做阈值，累加使用 FP32。
准入限制 reduction <= 2^24，使每个点积的整数和可精确表示；本轮最大
reduction 为 1,024。Metal 使用 safe math。8×8 simdgroup 矩阵 kernel
支持转置、不满 tile 的尾部和多批数据。它是共同的研究 kernel，**没有
证明达到 MPS 或设备最佳 GEMM 吞吐**。

本实验不用 ridge 预测真假。矩阵执行的是完整关系变换，数值输出直接
进入下一层。将来可让 ridge 拟合可证明保持信息的状态变换或选择计划；
本次收益不能归因于回归，也没有证明任意关系可压缩成小型固定向量。

## 验证

五个案例，每个跑三个 GPU 布局，分别检查 union 前后所有 F 位。独立
oracle 使用原始 P/Q、CPU union-find 和显式集合连接，不调用因子化
重写；不以某个 GPU 布局作为正确性参考。

所有输出逐位一致，且只含 FP16 0/1。每个案例都有 union 造成的实际
输出变化，前后都不是全零或全一。所有案例也都区分了上述错误的同列
因子合并。`tails` 同时覆盖非 8 倍数维度。

| 案例 | batch | x / z / y / o | rank | 每阶段输出位 | union 后新增输出位 |
|---|---:|---|---:|---:|---:|
| tails | 3 | 19 / 23 / 17 / 13 | 5 | 741 | 215 |
| small | 1 | 48 / 64 / 40 / 32 | 4 | 1,536 | 429 |
| narrow | 8 | 512 / 384 / 256 / 128 | 8 | 524,288 | 62,994 |
| single | 1 | 512 / 384 / 256 / 128 | 8 | 65,536 | 8,650 |
| wide | 4 | 256 / 256 / 192 / 96 | 32 | 98,304 | 631 |

这是此片段的有限数据检查及代数构造，不是对所有输入的机器证明，
也不扩展仓库的 sum-bits/native 语义验收合同。

## M3 Max 测量

日期 2026-11-12，Apple M3 Max，macOS 27.0.1。每布局两次排除的热身，
九轮交替顺序测量。输入和计划已驻留，运行中不分配图节点或读回中间
状态。以下每项都包含两次完整 DAG、一次中间 union 批次，以及重置
输入状态；最后的 F 矩阵物化也在计时内。

GPU 时间来自 Metal command buffer。另一个测量序列在同一 command
buffer 末尾把两份 F 复制到预分配 CPU 可读缓冲区，记录 host 编码、
提交、GPU 执行、读回和等待的总耗时。两个序列不能相减作阶段归因。

| 案例 | GPU dense / factor / cut (ms，中位数) | 含结果读回 dense / factor / cut (ms，中位数) |
|---|---|---|
| tails | 0.145 / 0.165 / 0.154 | 0.417 / 0.440 / 0.423 |
| small | 0.189 / 0.198 / 0.194 | 0.407 / 0.479 / 0.475 |
| narrow | 2.580 / 0.374 / 0.742 | 2.308 / 0.625 / 0.969 |
| single | 0.340 / 0.228 / 0.231 | 0.591 / 0.485 / 0.509 |
| wide | 0.346 / 0.615 / 0.244 | 0.590 / 0.885 / 0.489 |

`narrow` 的 factor/dense 含读回配对加速中位数为 **3.74×，9/9 更快**；
GPU 中位时间比为 6.89×。`wide` 全程 factor 更慢，cut 的含读回配对
加速为 **1.24×，8/9 更快**。两个小案例没有建立收益。九轮仅刻画
这一次短实验，不声称跨机器、跨负载稳定性。

`narrow` 的逻辑乘加数从 1,904,214,016 降到 125,829,120；私有 GPU
缓冲区从 24,871,680 降到 7,963,392 字节。`wide` 全程 factor 则从
4,998,272 增到 10,699,904 字节。这些数字含保留的输入和临时结果，
不是仅报告压缩因子大小，也不是进程 RSS。两个阶段的临时区分别保留，
未做生命周期复用。最终读回缓冲区在 JSON 中另外计费。

单独诊断的重置加 union GPU 时间约 10–25 微秒；它不等于主任务中该
阶段的独立贡献。分派和等待使小任务停留在数百微秒级。首次分配及
上传按布局记录，包含冷启动影响，未算进常驻执行时间。Python 生成、
编译计划及 oracle 合计约 0.81 秒；没有把 Python 当作 CPU 性能基线。
Swift/Metal 编译及文件导出不在执行计时内。

## 已完成与仍然缺少的部分

已完成：实际浮点 GPU 执行、压缩状态接续、相关分支交汇、局部 union
更新、无中间 CPU 调度、完全一致的有限语义检查，以及包含回退选择和
负收益案例的实测。没有增加 production 双重绑定存储或订阅结构。

未完成：从现有 Cell/Bake 自动提取该片段、从实际实例槽建立因子、
跨实例构造子判重、一般 congruence 闭包、实际返回见证、delta 归属、
有序效果、删除/世代及原源 Run 发布。这里只保留集合存在性，不能拿
它替代需要具体见证或顺序的消费者。反向传播训练和岭回归压缩也未做。

下一次生产接入必须由现有 Cell 定义证明这些连接及合法边界，并删除
对应的旧绑定展开和中间发布；要计入得到因子以及最终效果提交的成本。
还需要与有效的 CPU 位集/连接实现和优化 GPU 库比较。当前数据只说明
这是一种**确实能在 GPU 上高效执行的受限形式**，没有证明全量 egraph
的高效矩阵化或真实 EggFuse 的加速。
