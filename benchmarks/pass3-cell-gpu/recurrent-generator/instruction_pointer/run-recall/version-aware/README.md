# 规则 56 的版本依赖和 Higher 接口

基于 `039a6185`。在 sum-divisors 的十个真实见证中，生产者和端口号不足以描述消费条件。还有一条独立依赖：哪次提交使这个端口在当前图中获得了消费者需要的版本。原有具名祖先切片遗漏了能触发这些更新的区域外请求。仅在 Higher 里等待下一版本，十例都停在八步目标之前。

## 原生正对照与区域隔离

用相同的 CCP v0.1 Rust Cell Runtime，从初始图实际签发。原序重放保留 teacher 的实际请求和输入版本。第二个对照将原序编译成 627 个非空发布组，每个输入记录具名端口的可见版本序号。只有上一组收到真实提交回执、当前端口已发布且 Run 实际调度该规则，才允许签发。执行循环无须查询 teacher Run 编号。组间保留了历史先后约束，这是一份保守的离线程序，含区域外工作，不能据此声称已经恢复最小因果图。

两组均接受 17,341/17,341 次签发，执行 1,644 个 Run，记 11,905 个有效操作。终图、RHS、写入、调度、恢复、事件、repair、请求身份全部一致。按顺序对每个普通发布帧的调度、端口类型、版本、转发标志、字段哈希、退役及接受记录计算的 SHA-256 也完全一致。归档覆盖这 1,644 帧；另由 CCP 读完最终发布和终态。墙钟分别为 9.66 和 9.75 秒，含诊断记录，不能据此比较线上 EPS。[原序](control.json) · [回执驱动的发布组](control-dag.json)

| 独立派发的程序 | 原生结果 |
|---|---|
| 原十个具名祖先区域，各自隔离，按原 Run 和原版本提交 | 0/10 完成。环境变化后，原 Run 可能已不调度该规则。保留待提交和原生拒绝分别计数。 |
| 同一区域，首次可见版本 / 当前最新版本 / 指定的相对版本序号 | 三组均 0/10。代表性 59 步区域分别接受 39、39、38 步。等指定版本时有 21 步一直未就绪。 |

| 将十个区域取并集，同时保留原环境的一部分，按实际回执推进发布组 | 见下表。保留足够的外部工作可以复现目标端口；本实验未求得最小外部工作集。 |

## 哪些版本由区域外计算产生

对 387 个晚版本消费位置按见证和发布去重，得到 252 项；跨见证再去重为 38 个不同的端口版本。每次固定目标发布前的完整原生状态，只改变产生该发布的一个 seal 内所签发的请求，保留原生执行与 rebuild。比较同一地址的整个可见记录。134 次不同的原生前缀重放覆盖全集、仅区域内、仅区域外、无请求及逐个请求的对照。252/252 项均为“仅区域外可复现，仅区域内及空组均不可复现”。这项归因以共同前缀为条件。35/38 个版本有单个充分请求，另 3 个需要联合干预才能复现，逐个都失败。[逐地址干预和数据](causes.json)

例如，在完整前缀上单独执行请求 204，足以使 149 的 op 3 发布为版本 19；326 读取它。同一消费者的另一条线需要 148 的 op 3，针对该前缀得到的充分请求组为 179 和 190。在扩大后的 1007 隔离区域中，149 和 204 都实际接受了，但前者 op 3 仍仅观察到一次发布，版本停在 15。消费 326 因没有收到对应更新继续等待。可见“该写入请求已接受”和“指定端口发生了所需状态变化”需要分别核验。因果试验同时检查这两项。它只将共发布的指定请求作为守卫，未把同批接受本身解释为原生因果证明。

冻结 Higher 的接续器在 attach/首次可见时记录端口版本；后续失效时释放实例。原布局的内部线只有步骤索引与 op，不能表达特定的后续更新、其外部输入和等待条件。原生协议本身已经发出了这些版本变化。本轮把版本序号、具名更新回执和等待条件实现于独立诊断器，未修改 CCP。隔离试验尚未得到一个可完整执行、可从训练数据迁移的规则 56 版本模板。[既有接续器](../../region_owner.py) · [诊断派发](../../version_replay.py) · [因果扩张](../../version_expand.py)

## 入口的 47–172 个具名引用

逐一按 owner、op、version 拆开，十例都没有同一个 owner/op 因多个版本占用两个入口槽。每例有 42–163 个不同 op 来自同一个规则 375 初始化请求，其余 5–9 个是不同的初始事实，各有一个 op。后者涉及 bop-of-type、bpred-of-type、PureBaseType；在当前接口上必须显式提供，跨程序不能靠负数句柄猜测。未证明它们在所有等价程序中数学独立。

原生投影测试从真实回执取得 375 的 owner，按已编译的静态 PC 及当前版本读取每个端口的第 0 列。十例累计 1,078 次 CCP 具名观察全部成功，错版本和不存在的 op 分别被原生拒绝。所有目标 PC 都是 Recipe 的 let 操作，并逐一检查了声明表和发布表。由此，给定同一初始化结构和已选模板，入口可表示为 **1 个 owner 加 5–9 个外部事实引用**，独立选 owner 的机会由 47–172 降至 6–10。所有 PC 和版本检查仍需保留。各字段可能来自不同事实，同一 owner 不保证相同值。测试显式付费读取，没有测得等量的线上 Token 或搜索节省。这些 PC 来自本程序的已知布局，尚未验证换一个初始化程序也能复用。[每例投影、费用和反例](projection.json)

## 独立 Neural Execution 对照

保持原有 GNN、Edit Flow、所有权策略、CCP 和计费方式。用 sum 与 dot 训练 tape 中有正原生操作信用的 Primitive（每条规则最多取前三个）以及现有 donor 目录在原生完整替代中通过的、具有正操作信用的 Higher 作补充监督。首次使用 900 个 Primitive 目标和 62 个 Higher 目标校准原有 mark 权重，生成 18,049 个二叉决定标签。AdamW，固定 4 轮、种子 851，无评估集选 checkpoint。正操作信用是局部训练信号，不能估计长期收益。该对照使用既有训练目录；测试用因果区域未进入动作或权重。

## 复现与验收

工作目录为 instruction_pointer。ROOT 使用上轮 runtime-data 目录，包含编译程序、tape、memory、capture 和已编译的 cell_token_replay；FORKS 含 sum、sum-roll、grammar-benefit-fork-17118 的原生训练 fork。输入指纹见 inputs.json。OUT 可以指向新的临时目录。原生重放、外部生产者干预、投影和训练数据归因属于离线诊断；正式 Neural Execution 的两组仅选择模板及具名父端口，在线不读 teacher、反事实候选、版本序号或区域外请求组。原生操作隐含的 merge、rebuild 和发布保持原调度。没有将诊断器遍历义务或 Python 端记录的时间计作线上加速。

```sh
mkdir -p "$OUT"
ACTOR=run-recall/higher-scaling/weights/actor.pt
```
