# 实际 Pass 3 的冷启动、常驻推理与 GPU 热点

在相同的 M3 Max、冻结设备镜像和 CPU 对照上，最大的原始开销是残余入口匹配。完整 Pass 3 中，sum-bits 的该阶段累计 947 ms，占诊断 encoder 时间的 59.2%；dot-product 为 2,861 ms，占 83.2%。用已有事实的时间戳在 join 完成之前剔除不可能含新事实的前缀，这项工作分别降到 266 和 413 ms。CPU 基线是独立 Rust Cell CPU。[原始样本、分项、工作计数和核验](results/profile.json)

## 冷启动和常驻是两个问题

| 毫秒，中位数 | sum-bits CPU | GPU 原版 | GPU 优化后 | dot-product CPU | GPU 原版 | GPU 优化后 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 新进程，读入到导出并退出 | 134 | 2,402 | 1,682 | 132 | 4,284 | 1,840 |
| 已载入程序／设备状态，整轮推理 | 22.5 | 1,525 | 828 | 18.7 | 3,341 | 897 |

冷 CLI 每臂一次热身、八次交错、新进程，包含读盘、网络端口读取、图注入、计算及持久化输出。CPU/GPU 导出分别与已通过原生和完整图验收的基准文件校验哈希。GPU 原版两例启动 Python 并导入模块约 562 ms，设备准备约 139／141 ms，导出约 14／18 ms，其余进程与退出开销约 163／182 ms。各项中位数独立计算。常驻 GPU 在同一个 Python 进程内持有已编译 shader、已注入输入和缓冲区；每轮预算与原版相同，三种策略的全部六种顺序轮换。重置可变状态计时另列，每次都从原始输入重新推理。CPU 常驻列使用已解析的同一程序重复九次，只计执行。常驻 GPU 推理变快 **1.84×／3.73×**，冷 CLI 变快 **1.43×／2.33×**；优化后两例的常驻推理仍分别约为 CPU 的 37／48 倍。

为分离本来融合的代码，诊断查询先记录**实际选中的物理行**和编译路径，token encoder 只沿这些行提取参数。入口和 Spine 匹配包含查找与保存见证的位置；token 行包括投影已选见证、写入 token、排序和去重。单独的排序去重在基线为 39.8／41.0 ms。RHS 按获胜 token 顺序执行，包括创建接续标识和收集待发布见证；Spine 发布 encoder 按原序安装它们；因碰撞转发见证计入 repair。诊断使用额外临时区，冷启动及常驻基线都执行普通融合生产内核。

原版两个详细回放墙钟分别为 1.839／3.626 s，阶段合计 1.600／3.438 s，实际区间并集 1.595／3.434 s。预算上限 2,048 超过源 Run 数，报表另外记录终止后的空调用和完整 command buffer 时间。原 MPS CLI 另经 Xcode Metal System Trace 采集：按目标 PID 合并 Active 区间约 1.550／3.394 s，导出内容保持一致。原 MPS encoder 的标签无法细分其内部阶段，分项数字取自相同设备状态的具名 Metal 回放；没有用区间占比推断 ALU 利用率或带宽饱和。

## 为什么早筛有效？

半朴素规则要求绑定至少包含一条 epoch **大于等于**该规则水位的关系行。旧实现允许搜索到完整绑定后才检查。新路径为每张表维护“最近一次行版本变化”的保守上界，涵盖插入、有效函数更新、隐藏状态变化和 union 后的 repair。若查询中的所有表都比水位旧，可跳过该规则。否则找出计划中最后一个仍可能提供新事实的关系原子：如果前面的绑定已经过时，而且当前候选也过时，后继原子都无法满足增量条件，可立即丢弃该分支。删除记录只会令上界偏宽。一个旧 pivot 仍可与后来的新非 pivot 行匹配，普通全扫规则沿原语义执行。

sum-bits 的残余 DFS 循环从 **52,190,531 降至 13,146,825**，dot-product 从 **73,853,141 降至 15,044,873**。这是包括回溯的循环次数，与 CPU 的候选检查计数口径不同。只开表级过滤的三次常驻中位数为 981／1,593 ms；再只加分片过滤为 919／1,507 ms。表级＋前缀为默认。在相同进程轮换测量中，再维护分片时间戳，sum-bits 为 863 对 828 ms，dot-product 两者均约 897 ms；分片信息使 DFS 再少约 1%，需额外维护每张表 64 个整数。旧图册图 29 的冷 CLI 测量保留作历史对照。

优化后 sum-bits 的 repair 占阶段时间的 54.3%；dot-product 的入口与 repair 各约 42%。设备侧每次有 union 待修复时仍按顺序扫描记录，两例累计检查 392,115／314,234 个活记录位置；CPU 报告实际修复依赖 2,229／1,362 个，二者是不同工作单位。只用已发布键的哈希桶找碰撞对象，两个负载没有一致常驻优势，因此保持为独立消融。探索性的行签名过滤在 sum-bits 的设备同步处未完成，已撤出代码，不能据此报告速度或正确性。

## 如何验证与复现

所有正式配置以 1,428／1,535 次观察点的有序 RHS、有效写入、Spine 和最终类型化图为验收条件。诊断另比较物理行、原始父、类映射、所有 token 输入、写入与接续记录。默认优化重新通过完整 CPU 审计和隔离目录的无回填验证。生产路径照常只在 GPU 上做候选、匹配、提交与修复。测量时 CPU 读取的指纹和计数不会反馈给下一次推理。

```sh
root=/Volumes/EggFuseWorkspace/experiments/pass3-atlas-integration-20261120
weights=/Volumes/EggFuseWorkspace/experiments/rotary-axes-20261119/packed-1703/final.pt
~/.local/bin/eggfuse-job submit --kind compute -- /Volumes/EggFuseWorkspace/bin/run-eggfuse env PYTORCH_ENABLE_MPS_FALLBACK=0 python benchmarks/pass3-cell-gpu/profile/reproduce.py "$root" "$weights" /Volumes/EggFuseWorkspace/experiments/NEW-pass3-profile
```

复现需要 Xcode 的 Metal System Trace、Swift Metal API 和已验证的两份输入。驱动会新建目录，保存原始 xctrace、时间戳和轨迹，再生成小型摘要。当前路径使用 PyTorch 的自定义 Metal 内核；其他 ABI 的离线时延不可直接代入。生产 CLI 的 `--freshness 0/1/2/3/4` 依次为原版、仅表、表＋分片＋前缀、表＋分片、表＋前缀（默认）。`--count-work` 仅用于独立工作量普查，带计数的执行不参与计时。
