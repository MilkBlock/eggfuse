# Named port issuance on native EggCC Runs

Build the isolated native session with `python build.py OUTPUT`. Run `OUTPUT/session BUNDLE/program.json model.json > trajectory.json`, then `python compare.py EXACT_SESSION BUNDLE trajectory.json result.json --plans PLANS`. The separate reference uses baseline mode. The issuer gets current visible typed ports. It names every independent table premise with its physical address and epoch. The verifier only dereferences named parents. The frozen role, context and freshness gates originate in join-port-diagnosis. Compiled layout ordering, candidate traversal, fingerprint confirmation and packet assembly remain issuer work. The source scheduler, verifier guards, RHS and repair run on CPU.

The scan control visits typed banks. The routed treatment builds lossy 10-bit pages from the input columns already bound by the prefix, including literals. A row satisfying the full fingerprint check necessarily has the requested page. A seminaive rule may require a fresh row at the current step when no other remaining table has a fresh row. Both controls cap row visits at 500,000 per rule per Run and abstain on overflow. Encoding, watermark inspection, page construction, summary reads, probes, scoring, and receiver reads are reported separately.

With the original source-first layout the routed treatment recovered final graph, schedule, ordered RHS, writes and all non-resume events on six of eight workloads. See page-results.json. The strict resume-inclusive trace differs even in those six. Rules 144 and 566 alone exhausted the budget on 3mm and deriche. Counts after the first divergent Run are outside the aligned trajectory. These are native correctness and work diagnostics. Neither full read-cost speedup nor search replacement by a general neural policy is established here.

For a three-table query containing two aliases of one table, the compiler can start from the third fact when that fact binds a separate endpoint of each alias. In rule 144 the Concat fact supplies both SubTuple outputs; in rule 566 the view supplies both expressions for HasType. This choice uses static slot incidence. The issuer still has to locate every parent, and the independent verifier still checks the ordered named tuple. It uses the same model.json and row-visit budget as the source-first study.

bridge-results.json records all eight native runs with that layout. Every source Run, ordered RHS digest, write digest, graph mutation trace and final graph digest matched, with zero budget exhaustion. All eight still differ on the strict resume-inclusive trajectory. In 3mm alone, 32,079 packets were rejected and 752,240 named receiver reads were performed. These costs matter even with full agreement on committed bindings. Compiled traversal and candidate enumeration contribute to coverage, so this does not measure the neural share of search eliminated. The two previously failing programs informed the layout change and are regression cases.

## Learning which input to read first

For a connected two-table rule the compiler prepares both orders. At each eligible Run the optional network sees the two bank sizes and fresh-row counts, plus indicators for an empty fresh frontier and the page-index size threshold. These counts already exist at that point. A shared 16-unit tanh scorer evaluates each ordering (160 exported scalar weights and biases; the common output bias cancels). Only then does the issuer build its root summary and traverse the selected layout. The wire packet always names both actual parents in original source order. Three-table bridge selection and all other rules retain the previous compiler plan.

Training uses 4,096 randomly generated two-bank memories with an equality slot. Both candidate orders are traversed for each memory. The loss is the expected number of candidate visits under the two-action softmax. The training traversal counts lossy summary hits, follower page sizes, and the fresh-only gate. It doesn't simulate all source rule guards, extra shared columns, or native data distributions. No EggCC trajectory is a training example. The independent 2,048-bank test includes a smaller-first policy and an oracle choosing the cheaper measured order after both traversals.

Run the same session build with model.json for the compiler order, order-model.json for the learned order, and the generated smaller model for the smaller-first control. At equal scores both keep compiler order. The model files have the same port acceptance gates. The smaller control uses the same scoring implementation to isolate action choice. Each native arm gets a separate exact process comparison as described above. To reproduce training and validate the three-arm results:

```sh
python train_order.py order-model.json order-training.json --ablate --smaller-control /tmp/smaller.json
python check_order.py ARTIFACT_DIRECTORY order-results.json
```

order-training.json records the linear, short-training, all-fresh training data and wider-network interventions with two initialization seeds. All-fresh training removes differential freshness from training examples. The held-out cases stay identical. Candidate visits count every row reaching the budgeted traversal, including rows subsequently excluded by a freshness test. Summary reads, epoch reads, route construction, probes, network decisions and receiver work have separate counters. The visits objective does not measure wall time.

Across eight native workloads, compiler order visited 203,725,652 candidates, smaller-first visited 199,299,557, and the learned policy visited 160,409,353. The learned policy reduced visits on each individual workload against both controls. It changed the direction in 17,342 of 34,192 eligible decisions. Compared with compiler order it raised page construction from 39,963,266 to 50,798,672 rows. All three arms had identical accepted and rejected counts and named receiver reads per workload. All eight strictly resume-inclusive traces differ from exact search. The training loss targets issuer work; it leaves the number of independent proposals unchanged.

order-timing-sum.json contains six sum-bits wall times per arm after one warmup per arm, interleaving rotated and reversed orders. Each timing starts a fresh release session, parses the same program, runs the audited native executor and serializes its trajectory to a null sink. The separate exact comparison is excluded. Medians were 263.0 ms (source), 270.8 ms (smaller) and 265.6 ms (learned). Lower candidate visits did not demonstrate a latency gain over source order here.

## Declining a scalar-inconsistent packet before signing

The issuer optionally carries the small i64 value of a port alongside its structural fingerprint. Bake projects the readout onto already bound Cell slots or source literals. For a Unit comparison the model scores its two operands; for addition/subtraction it predicts the result and compares it to an already bound destination. These six affine readouts were fitted by backpropagation on 4,096 random pairs per operation, with extra near-boundary and equal pairs. There is no workload trace in training. The native loader checks all pairs in the supported interval [-16,16] against each exported operator before enabling rejection. Outside the interval, with an unavailable operand, or with an unsupported primitive, the normal named packet remains eligible. These gates encode deterministic primitive semantics. This comparison measures the effect of having them at issuance; an exact scalar filter covering the same domain would make the same decisions.

Run train_scalar.py model.json scalar-model.json to reproduce the readouts. Build the session here, then use scalar_study.py EXP NATIVE_SESSION EXACT_SESSION OUTPUT. Each workload runs once per model and once in a separate exact process. Each arm counts source-attributed new constructor witnesses still present under their original physical identity at the endpoint; issuer gates never see the birth ledger. The experiment checks the digest of the surviving identity set across arms, every Run's schedule and ordered RHS, writes, mutation events and the final state. Each suppressed packet must account for exactly one fewer receiver rejection across the workload, and verified counts must agree. The full receiver still checks the primitive on any packet it receives. All issuer-side structural traversal remains in place. Report this audit's visible-nodes/paid-packets separately from strict Spine-aligned FEPT: the resume-inclusive trace differs. No end-to-end acceleration or additional large-template takeovers follow from reducing failed issuance.

The optional wide_scalar input representation applies those same certified comparison weights to all signed i64 operands. Each operand independently flips its sign bit and splits into sixteen base-16 digits. From most significant to least, the readout evaluates each pair in both directions. At the first asymmetric answer its decision determines the whole comparison; if all digits tie, the final decision handles the strict or inclusive boundary. Arithmetic agreement still uses the bounded readout. The additional port_distinct arm suppresses a Unit != proposal when two bound ports carry exactly the same integer or the same Eq identifier. This last gate is a deterministic identity check; unknown payloads and distinct Eq identifiers are left alone. No hash collision can authorize this omission. The four-arm scalar_study.py --wide experiment isolates this change from the numeric model. check_scalar_edges.py COMPILER NATIVE_SESSION EXACT_SESSION covers extreme signed integers, compares against independent native rule execution, and rejects a corrupted readout.
