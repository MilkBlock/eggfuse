# Actual-history admission check

This is a one-candidate work-count check of the actual Cell runtime at
`a4b14c4b`, not a speed benchmark or standalone prototype. The sum-bits seed
is the saved `final-checks/sum-baked/program.json` artifact, with its optional
`iterative_bake.completion` removed and checksum recomputed so that structural
proofs are regenerated by the current compiler. The exact prepared source and
candidate hashes are in `sum-bits-work.json`. Raw generated programs remain
untracked; reproducing these exact numbers requires that same seed artifact.

```
cargo run --locked -p eggfuse-cell-compiler --features iterative-bake,sparse-cells -- iterate --program PREPARED_SEED.json --output out/queued-union-admission --objective ripsat-completion --score measured-work --rounds 1 --trial-limit 1 --local-congruence true
```

One of five ranked proposals was tried. The selected ordinary observed join
`(left=3, output=2, right=5)` saved 370 key lookups and 205 constructor requests,
but added 534 history allocations. The equal-weight total is +2,603; this is
not a latency prediction. All graph/schedule/ordered RHS/write/resume audits
passed, and the next round used the exact measured candidate. This does not
replace the separate native sum-bits semantic acceptance script.

Ripsat structural search checked 24 proofs and admitted zero extensions.
Therefore the reduction must not be attributed to terminal-Union recognition.
The retained pair's most recent sample is at Runs 1,220→1,223, beyond the raw
trace cutoff; bounded pair evidence remains useful without reconstructing a
missing full event chain.

The next opportunity is the winning join's actual history/publication path:
`StageSpine::begin_effects` creates 369 joint frames and copies 311 query facts;
`Started::remember` charges the 534 history allocations;
boundary publication reads joint outputs 534 times. Before removing any of
these, establish which frame owns the retained results and which query/output
slots later consumers actually read. Shared Entry, delayed publication,
liveness and source Run ordering remain obligations. No additional runtime
tracking was added for this diagnosis, and no saved operation is claimed from
these maintenance costs yet.

## Rejected exclusive-owner reuse experiment

A temporary change to `History::retain_results` reused an existing uniquely
owned `Rc<Trail>` when the compiled history depth was one. The same one-trial
sum-bits admission replay still reported 534 history allocations and +2,603
net operations. The completion/query receipt regressions passed, but this
workload showed no benefit, so the runtime branch was removed rather than
adding an extra ownership probe to every such capture.

The 534 counter is not a total allocation census. `Effects::begin_joint` also
allocates its slot vector; the 369 joint-frame creations are already charged
separately by `Work::read` as `joint_history_frames`. Adding that count again
as a new scoring term would double-charge the same creation. Future allocation
measurements should distinguish owner and slot-buffer storage without changing
credits merely to improve a score. The next target is captured-slot demand and
lifetime, not an unmeasured allocator substitution.

## Capture demand audit

The measured artifact has only two states with nonempty supply. State 12
(rule 143) retains `Query(0)` (Get witness) and `Effect(1)` (Single result).
State 33's completed consumer (rule 137) uses both at back=1: output operation 1
reads the query witness, and output operation 2 reads the constructor result.
Its checked completion sources are exactly `(143,0)` and `(143,1)`. The relevant
artifact entries are preserved in `sum-bits-work.json`; neither producer slot
is dead, and the query read/write cannot simply be removed.

The remaining structural opportunity is the consumer's result-owner wrapper:
its entire output frame is already a static projection of that donor. Explore
publishing through the original owner plus that projection, rather than
allocating a fresh owner only to contain a projected Results value. This needs
a view-aware lifetime/slot lookup design; it is not the rejected unique-owner
mutation experiment. Rule-specific ResultPort identity, deferred publication,
actual foreign constructor addresses and retirement checks remain mandatory.
No wrapper allocations have been eliminated by this audit.

The subsequent [projected-owner implementation](../cell-projected-owner/README.md)
removes 165 of the combined catalog's 534 history owner allocations while
retaining both live slots. It also grows inline history handles by eight bytes;
the work reduction is not yet a speedup or total-memory claim.
