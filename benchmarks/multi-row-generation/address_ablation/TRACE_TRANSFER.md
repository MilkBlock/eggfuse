# 把图 03 的地址打分器应用到图 20 已生成的 Pair

图 20 在盲测配对中遇到过这样的情况：指定来源由 `q` 换成等价的 `p`，合法性保持不变，而且两个原始父都已经发布，消费者仍选不对父。该诊断读取图 20 留出规则 134、135、143 和两个 `pairwise` 种子的实际设备输出。每份轨迹有 128 张图，包含原来的全部盲测、非盲测和四种动态状态。

图 20 的 Request 已含 `(read_owner, read_handle, required_owner, required_handle, tag)`。打分时只取公开的指定来源 `(required_owner, required_handle)`。候选来源读取实际生成的 Pair 的两个已传输字段 `(owner, handle)`。每个请求在 GPU 上对原来的 8 个候选槽一起打分，包括未激活、非法和重复的槽。没有从 CPU 逆向查找正确的生成位置。两个固定的地址布局完全覆盖同样的 16 个公开身份。

| 布局 | Row | 行内 token 位置 | 端口 | 地址空间 |
| --- | ---: | ---: | ---: | --- |
| owner-row | owner | handle ÷ 2 取整 | handle mod 2 | 2 × 4 × 2 |
| split-handle | handle ÷ 4 取整 | owner | handle mod 4 | 2 × 2 × 4 |

每个图 03 模型使用自身已训练的第一个指针头 `address_scores(stage='make', ...)`。这个头只接收公开地址。图 20 的 56 维 token 与图 03 第二个指针头的专属 latent 不兼容。这里测的是地址打分权重在另一前沿上的迁移能力。

保留两个不同的指标。

1. **发出请求后，选对来源的能力。** 对原来的每条请求打分，随后用图 20 的运行时分区重放判断该请求是否合法。CPU 审计检查被选父的真实激活位、其原始 A/B 端口构成的合法绑定、传输字段以及指定物理来源。如果多个实际有效槽具有同一要求的来源，选择其中任何一个都可以得分。同时报告只对来源、选中失活槽、选中非法生产者，以及最高分相同的槽中是否包含正确父。所有 `ready` 分母只使用至少有一个真实正确父的合法请求。
2. **替换原消费者已发出动作的父指针。** 原 `finish` 的每个激活位、所选 Request 槽和等价判断保持原来的冻结输出。GPU 只将其父指针换成地址头对该 Request 的预测，并沿所选实际父重新投影五个结果字段。随后运行原来的 `paired_controls`，重算同类换源的一对请求是否都准确发出。它与图 20 已报告的 0/30、1/30 和盲测 0/6 使用同一批探针、同一完整发射口径。漏发、重复或挑错 Request 仍由原模型承担。

同一原始 frontier 上需要原模型先学会生成和激活正确的 Pair，单个地址头不能创造缺少的父。训练好的 ranker 也不能凭相同的 `(owner, handle)` 区分内容有误的同地址槽与有效槽。原系统的实际延迟、真实跨 Run 的完整神经解码，以及换坐标后的重新训练不属于这次离线指针干预。

在已训练好的八个地址检查点上运行：

```sh
~/.local/bin/eggfuse-job submit --kind compute -- \
  /Volumes/EggFuseWorkspace/bin/run-eggfuse env PYTORCH_ENABLE_MPS_FALLBACK=0 python \
  benchmarks/multi-row-generation/address_ablation/trace_transfer.py \
  /Volumes/EggFuseWorkspace/experiments/rotary-axes-20261119 \
  /Volumes/EggFuseWorkspace/experiments/rotary-axes-20261119/trace-transfer.json \
  --figure20-root /Volumes/EggFuseWorkspace/experiments/eclass-ports-20261119
```

完整位点选择保存在外接盘上的 `trace-transfer-choices/*.npz`。报告记录输入、模型、输出的哈希、各留出模板的分母、同源/同分歧义及四个模型配对种子的重放结果。

## 冻结轨迹结果

在 `owner-row` 布局，四种地址头对两份生产者前沿都选中了正确的 `(owner,handle)`，每份 780/780。但选择**携带正确值且已激活**的父槽时，1703 只有 536/780，1709 为 752/780。相同来源可以出现在多个生成槽，其中只有一个有效。1703 有 248 个请求看到了相同地址的多个槽，244 次选中了失活副本；1709 的对应计数为 182 和 28。两组的全部 780 个请求都有正确父位于最高分的同分集合内。我们保留网络原始 `argmax`，没有按标签解决这些平局。

以下右侧两列沿用图 20 完整发射指标，冻结原始 `finish` 活跃槽和 Request 选择。左侧检索指标仅检查已知合法请求的两个成员是否都指向有效来源。所有数字都使用相同的 `owner-row` 布局，四种头在这里结果相同。

| 前沿种子 | 状态 | 单独检索／30 对（盲／6） | 原完整发射／30（盲／6） | 替换父指针后的完整发射／30（盲／6） |
| --- | --- | ---: | ---: | ---: |
| 1703 | post | 11（0） | 1（0） | 10（0） |
| 1703 | external | 11（0） | 0（0） | 9（0） |

三条留出规则的整图输出也按原审计重放。每个种子共 384 个非空图，替换父指针后完整图从 61→136、65→265。原本没有正确激活或没有选对 Request 的输出依然失分。post 和 external 包含同组不同状态，两个分母各自报告。

`split-handle` 采用训练中未见的 4 个端口。下表给出所有本应读取且正确父存在的请求中，实际选择有效父的次数（分母均为 780）。

| --- | ---: | ---: |
| flat | 536 | 752 |
| two | 452 | 572 |
| three | 516 | 710 |

交叉交换地址模型的两个种子、保留原生成前沿后，`owner-row` 的有效父数及配对发射数全部不变。`split-handle` 的 two 头还受训练种子影响，在固定图 20 的 1709 前沿时改用 two-1703，选中有效父从 572 升至 676。该小型外部前沿没有显示三轴头稳定超过包含端口信息的 packed 头。真实激活状态和同地址重复是本次诊断另外暴露的约束。
