# 高阶 Cell 的迭代 Bake 计划

**首个可交付目标**是在完整 Pass 3 中，让网络签发一个带未决子端口的实例；Rust 根据真实父端口的精确值选择子块，在原消费者 Run 开放结果。在相同候选、权重和验证器下，测一份条件模板能省掉多少子提案、独立验真、查表与分配，并核对整轮墙钟。本文件是实施计划。已有实测和本次只读轨迹核查均单独标明。

## 先做哪一个模板

第一例选 `SubTuple`。规则 138 对 `SubTuple(expr, a, b)` 在 `b > 1` 时生成新的 `SubTuple(expr, a+1, b-1)`。新构造器的长度为 1 时可进入规则 137，大于 1 时可继续进入 138。因此生产者的**同一个效果位置**就能展示不同形态。[原始规则](../workloads/pass3/inputs/common-prefix.egg)

立项时用已有的 `transactions.collect` 只读检查四个训练家族，按生产规则和效果位置分组，仅保留非常量长度。规则 138 的效果 5（从 0 编号）得到下表。计数单位是发布事件；一次发布后来是否真的触发消费者，要再按发布票据回连到提交记录。[采集逻辑](../benchmarks/pass3-cell-gpu/verifier-placement/transactions.py)

| 训练程序 | 新长度 = 1 | 新长度 > 1 |
|---|---:|---:|
| affine-twins | 11 | 36 |
| clamped-ramp | 26 | 88 |
| segmented-prefix | 25 | 69 |
| window-laplacian | 20 | 58 |

例如，两个实例使用同一模板。A 的父输入长度为 2，效果 5 产生长度 1，Rust 为它绑定 137 的入口；B 的父输入长度为 4，效果 5 产生长度 3，Rust 为它绑定 138 的入口。网络可以在两个值算出来之前签发实例。若本次父 RHS 输掉去重，子端口保持未发布。若父效果返回已有行，子端口必须引用实际返回的事实及本次发布版本。规则 145 还需起点为 0 且长度与另一张表吻合；即使 137 已就绪，145 仍可独立成立，必须保留这项义务。[消费者分布](../benchmarks/pass3-cell-gpu/interactive-policy/README.md)

## 模板、实例与验证的契约

| 放置位置 | 信息及所有者 |
|---|---|
| 共享模板 | 编译器保存父端口类型、请求的精确程序、读取边界、分支谓词、各分支的消费者入口／端口接线、尚需检查的外部前提。模板 ID 绑定源程序和库版本。 |
| 实例 token | 网络选模板及不能静态推出的来源。实例记录稳定的自身身份、实际父 token 与效果端口、尚未确定的边界引用。子分支可先引用一个有类型的待决端口。 |
| Rust 实例状态 | 保存待决、已解析私有、已公开或已失效状态，以及实际发布票据、所读版本和支持关系。已解析的子块共享模板内的接线。 |
| 事后审计 | 记录请求结果、选中分支、原 Run、真实 RHS 序号和新建 Cell ID。训练可读；在线生成不能读未来提交。 |

请求分三类处理。能由字面量或生产者既有运算推出的值直接折叠或复用。依赖动态端口、但答案唯一决定分支的请求留在 Rust，允许同一版本及同一语义读边界内复用一次结果。只有精确答案仍会影响模型对其他合法后继的选择时，才开放可选回执。首版使用 CPU 网络与 Rust；回执可以是同进程的分支码。已有事务回放显示，逐项返回动态整数的同步成本可能远高于延迟求值。[已有回执对照](../benchmarks/pass3-cell-gpu/verifier-placement/README.md)

每条分支的证明义务为：父来源合法；guard 在该源读视图为真；余下 LHS 已检查；RHS 使用原有序提交点。互斥性只对编译器证明互斥的分支生效。可同时触发的分支保留多个后继，未覆盖的入口继续按源语义枚举。缺前提是待决；关闭整项源义务需要覆盖证书或已计费的精确补查。

## Bake 每一轮做什么

1. **编译请求候选。** 从类型化 LHS、RHS 和 merge 程序倒推能影响后继选择的字段。第一版只实现有界的 i64 比较、字面量分支与完整唯一键读。把谓词规范化为“父效果端口、字段、运算、常量、读边界”；重编号、物理地址、绝对 Run 号不进模板键。区分算出的候选端口和合并后的可见端口。
2. **一次轨迹，批量提取。** 每个实际父发布记录来源与票据、可用 guard 输入、观察版本、同批可选消费者；事后关联真正消费该票据的 RHS、重复、未消费和失效。按同一父接口聚合兄弟分支，分别统计全源与模型获胜父的支持度。数据先按程序家族划分，再做发现和拟合。源代码中可证明的分支在未被采样时仍保留语义。
3. **形成一个条件模板。** 共用父证明和请求，将相同结果的端口接线合并；只在后续成员或连接确有差异的位置保留分支。校验静态类型、每个字段的来源、guard 的生效边界以及外部读者。等价模板的判据是：对同一合法边界输入、版本和调度，产生相同的可观察端口、义务和有序效果。首版只合并能用规范化程序及接线相等证明的项。
4. **按边际收益选一批。** 对候选 K 比较：省去的重复父验证、子提案、查表与中间记录；新增的请求、待决状态、失效修复、库字节和分派。两个模板覆盖同一 RHS 或同一次查询时只计一次。先按估计净收益排序，再用启用 K 的真实 CPU 执行检查估计；高频或分支熵高都不单独构成准入理由。
5. **实际执行，再长一层。** 把已接受的 K 作为下一轮基本单元，从它真正发布、被读取的输出端口接入下一块。只有无外部读者、Spine 或 repair 需求的中间状态才退役。保留活端口的稳定引用。第一版建议沿用现有库的深度 4、成员数 8、每轮最多加入 8 项、库总量 64 的预算；条件程序另记 guard 数与分支边数，首轮只允许一个分支点。递归的 138 可复用同一模板，跨 Run 新实例受源调度约束，不在 Bake 时无限展开。没有正边际收益或开发集回退时停止增长，保留上一轮库。[已有迭代器与限制](../engine/cell-runtime/src/iterative.rs)

新增格式宜作为现有线性 Join 的版本化扩展。旧库仍按已有接线运行；新增模板引用可共享的请求程序和后继列表。实现优先复用现有编译端口投影、已发布的真实父引用和 Rust 的求值语义。[根配方](../benchmarks/pass3-cell-gpu/joint-root-cells/recipe.rs) · [合并子配方](../benchmarks/pass3-cell-gpu/joint-merge/child.rs)

## 实施顺序与决策门槛

| 阶段 | 交付物 | 决定是否继续的证据 |
|---|---|---|
| P0 机会清单 | 在四个训练家族列出全部候选接口及前述计数，再回连后继提交。增加两种分母：至少实际走过两个分支的模板占比、这些模板覆盖的实例占比。 | 找到跨程序复现、确有动态分支并有真实消费的接口；限定模型实际能签发的子集。 |
| P1 单请求在线 | 先在 sum-bits 接通 138.effect5 的封存、解析、原 Run 激活。先固定父提案流，隔离验证器差异，再让同一 CPU 策略在线独立发行。 | 两种分支均出现实际消费者；错父、过期、父未提交、条件成立但无消费时均按源语义处理。 |
| P2 可变状态 | 接入 `candidate_size`／`visible_size`，以及 union 后的来源验证。票据过期时只退役依赖该票据的证明，仍有独立支持的结论继续存在。 | 用真实例验证：#3240 候选 4、可见 1，#7039 后来读到 1。另测同类不同父与已转交端口；禁止默认根分配时单列结果。[数值实测](../benchmarks/pass3-cell-gpu/numeric-projection/README.md) |
| P3 迭代与泛化 | 固定训练／开发家族。每轮输出库、逐模板边际工作量、实例状态峰值和解码审计。整库冻结后跑 sum-bits、dot-product、留出 GEMM-bias-ReLU 与 stable-argmax，沿用种子 1703／1709。 | 检查库能否从单 guard 长到跨 Run 的大块，并实际移除原中间工作。评估候选库时禁止用留出轨迹选阈值、选轮数。 |

**消融要分开回答两个问题。** 第一组固定源程序、见证和请求输入，比较原线性 Bake＋普通 Rust 条件分派、平铺的专门化子模板、共享父证明的高阶模板。普通 Rust 分派是必要基线，能测出仅把一个比较改写成分支表有多少收益。第二组固定高阶库、模型权重与提案预算，比较预发全部候选后剪枝、封存符号分支由 Rust 延迟分派、必要时批量返回 guard 给下一次神经选择。再在相同每 Run 动作配额下比较，防止把多发提案记为分工改善。

每组都报每模板的发行数、实际走过的分支、父证明复用次数、实际不同子 RHS、未消费／失效子数、未决实例峰值字节、库存储、完整分配曲线及整轮墙钟。提前达到某个 RSS 水位要与后来实际兑现的子实例一一对应。用同机交错的常驻计时做取舍，冷启动单列。

**保留标准。** 逐 Run 核对有序 RHS、有效写入、Spine、union 和最终图；逐程序、逐种子维持至少 98% 的神经来源 RHS 和直接由证书构造的新物理 Cell，并另跑关闭补查。分支数、请求通过数和事后最优覆盖均不计作神经提交。只有相对普通 Rust 条件分派减少了可归因的工作，且端到端收益能在重复计时中复现，才把高阶形态纳入默认库。若只省下字节或只证明机制正确，保留为实验结果，分别报告。[当前验收分母](../benchmarks/pass3-cell-gpu/coverage-target/README.md)

## 两轮实测后的实施优先级

本节记录完整 Cell CPU Pass 3 研究后端的首次验收。离线只用四个训练程序发现模板。首轮选择规则 138 的效果 5，执行后把真实父发布与后来提交的子 RHS 回连；第二轮从这些轨迹选入 144、142、140 的效果 2。子块到源消费者 Run 才能提交。表中一个“子 RHS”对应该模板实际取得的一个源 RHS 序号。源 RHS 总数包含所有提供者。两个种子 1703 和 1709 的这些计数一致。[训练轨迹与库增长](../benchmarks/pass3-cell-gpu/higher-order-bake/growth.json) · [逐组结果](../benchmarks/pass3-cell-gpu/higher-order-bake/results.json)

| 留出程序 | 首轮子 RHS | 第二轮子 RHS | 全部源 RHS | 最长实际接续 |
|---|---:|---:|---:|---:|
| sum-bits | 14 | 90 | 7,265 | 5 |
| dot-product | 15 | 44 | 6,704 | 6 |
| gemm-bias-relu | 63 | 194 | 15,462 | 10 |
| stable-argmax | 30 | 95 | 8,190 | 7 |

以 sum-bits 为例，种子 1703 的真实执行中，第 106 个 Run 的 RHS #692 产生一个子来源；Run 110 的 #875 用该来源进入 138，Run 114 的 #1038 再从 #875 进入 138。每一步都能追溯到已签发的父及实际效果位置。递归版本继续扩大了每份证明可描述的链长，四个负载上的实际获胜子 RHS 数与第二轮非递归版本相同。八组逐 Run 的有序 RHS、有效写入、Spine、union 和最终图均通过对照。sum-bits 在种子 1703 下，第二轮普通 Rust 分派为 104.64 ms，高阶递归为 105.83 ms；种子 1709 下分别为 103.34 与 100.39 ms。当前证据支持继续研究模板增长，尚不足以把递归设为速度默认项。

1. **先选共享前提贵的兄弟规则。** 用类型化计划比较两条规则的全部父端口、查询顺序和可见版本；只在共用这些输入时共用一次父见证生成与验证。四个训练程序筛出规则 509/510。相同输入先求一次精确比较，再分派小于、大于两个后继；相等时两个后继均不提交。检查源水位和中间写入；不能复用的 Run 单独执行。逐项报告少走的父行、少签发的多父 token、少验的父元组、重复读取，以及增加的生存期和每种子配对耗时。
2. **再让等待中的实例实际退役。** 在源提交或版本失效时释放相应请求。比较顺序追加和槽位复用，记录待决活跃数、底层分配容量、高水位、累计分配与整轮耗时。槽位复用必须携带代际检查；晚到的旧引用不得指向复用该槽的新实例。退役前有外部消费者的端口保留稳定来源。
3. **最后扩展到可变读和模型回执。** 先以 Expr-size 的整数加法和同键 min 为例验证候选值、提交后的可见值、读版本及读取次序。固定模型、模板与发行预算，比较整批延迟求值和一次批量回执。只有返回值能改变下一波独立父选择并降低总耗时，才引入交互。覆盖不足记为未完成义务，精确补查的工作单独计费。

每次扩库后，保留上一轮可执行库并交错计时。优先考察每个新增模板独占省下的父遍历、验证和中间状态；这些量还要扣掉请求维护、分支选择及外部通知。增加子 RHS 数和链长可证明跨阶段机制生效，独立的完整墙钟对照决定是否启用。

## 训练合并门控的数据从哪里来

先问当前调度能否提出这个动作。对于“活父接纳即将生成的子成员”，可以在父发布之前固定源图、权重和调度，分别回放逐叶及组合分支。训练键绑定实际 producer、effect、发布代次和消费位置。对每份证书记唯一子 RHS、实际少走的入口、少做的重复检查、少发的中间票据，同时按程序计入所有外部索引扫描。这让未被消费的发布也有诊断价值：如果它能证明某个后继始终不可能，它可以省掉多次空遍历。

对于“两份完整实例都已有物理 owner，再合为一份”，还须记录左右旧 owner、代次、全部成员、外部读者、目标 owner 以及哪些旧记录真的退役。旧版精确存储调度显式跳过全部成员均已完成的候选。这样的分支即使在源程序中存在潜在机会，也很难通过观察常规运行直接得到成功或失败样本。可以用小图合成可合并、成员遗漏、外部引用和代次变化的对照；随后在独立副本上对真实阶段快照主动试一次合并，与原调度比较可读端口、union 后 repair、原 Run 有序效果和净资源变化。缺少对应真实签发凭证时，把这类数据标为反事实训练数据。物理接管的新鲜子、两个已存 owner 的合并、跨 Run 逻辑证书各自计费。

目前四个训练程序产生 689 份父发布，295 份后来赢得子 RHS。完整的候选门控只有 52 个不同的八维输入向量。21 种输入同时出现赢家和非赢家，意味着仅凭同一组可见性特征无法恢复全部后续归属。小型合成调度器能补版本替换、重复认领和递归等稀有案例。奖励是否成立仍可通过两个真实源路径的差分取得。固定两种预训练的样本预算，在四个评估程序、两个种子上，奖励兑现、局部工作或完整维护成本时，两种预训练分别在全部八组作出同样的逐实例决定。将真实门控数据缩至 96 份后，兑现及完整成本两组亦在两锚点、两个种子上全部一致。[真实事件与奖励契约](../benchmarks/pass3-cell-gpu/merge-reward/README.md) · [物理奖励与所有权对照](../benchmarks/pass3-cell-gpu/physical-composition-reward/README.md)

### 两个已经存活的 owner 怎样取样

以 dot-product 的 Run 20 为例。准备阶段把源成员分到两个已有 owner，成员集合分别为 `{275,298}` 和 `{314}`。合并提案只列 `{298,314}` 会漏掉仍然存活的 275，必须在搬移前拒绝。完整提案沿用三个外部读者已经持有的端口，释放一个旧 owner，操作内净减少 124 B，同时临时多占 304 B。一个四阶段小程序也释放了一个旧 owner，却净增加 224 B。相同的“合并成功”标签会给这两次操作相同的正奖励。这个实验使用主动准备的初态，签发者是控制程序。正常 pooling 在 dot-product 中访问了 278,811 个涉及两个 owner 的 component，其中恰好覆盖双方全部成员的次数是零。[真实干预与未改动调度的机会统计](../benchmarks/pass3-cell-gpu/existing-owner-transfer/README.md)

下一组训练消融应保持模型、静态模板、训练更新数与动作预算一致，分别用真实预热、合成预热，再接入相同的 Rust 成本反馈。在程序家族切分后，从训练侧接口生成成对的 `keep` 和 `compose` 初态。只改一项条件，例如漏掉一个成员、源代次过期、仍有外部读者或合并后遇到一次合法 union。编译器给出允许的模板和端口，Rust 验证器决定实例是否能接管。外部读者要求原端口持续可读。有读者的实例也可以合法合并。

每个样本保留两个目标。第一个是当时的动作是否合法，记录拒绝原因。第二个是动作在同一源初态中带来的实际成本差，分别记入口访问、证明、物理分配、repair、峰值和完整推理耗时。训练时只暴露提案前可读的特征。合成成功率不能估计部署中的机会密度，评估须在完整留出程序中分别报告自然可提案次数、签发与验证成功次数、最终净收益；对主动准备的 owner 对另报条件成功率。这样，训练可以过采样罕见分支，部署收益仍由自然工作负载决定。

配对奖励现在已接入 Rust 的物理决策边界。九参数门控看到当时的成员、槽和操作数量，用带两个真实 owner 代次的回执决定保留或合并。训练中 16 个合法合成案例强制合并全都多用内存，10 个合法工作负载案例有 2 个省内存、8 个持平。相同混合数据上，直接优化门控期望回报学到全部保留，回归配对字节差则能区分一部分机会。它在四个准备好候选的真实程序中获得 192／416 B，避开额外小样例的 224 B 损失。这四个程序按自然调度都没有可接管的完整 owner 对。提高自然机会密度要改变前序放置，给已有动作加大奖励无法创造候选。[训练与留出程序的原生回执](../benchmarks/pass3-cell-gpu/owner-action-policy/README.md)

## 用标量请求改变下一次签发

规则 144 提供了比「给已选子块打分」更直接的应用。对于 `SubTuple(expr, a, b)` 和 `SubTuple(expr, start, c)`，LHS 要求 `a+b=start`。编译器从已封存计划中读取操作数的来源，证明可由第一实例的槽计算结果，并在另一父实例找到目标端口。Rust 严格按源 i64 语义求值，使用与独立父选择同一组权重得到结果签名。不同签名可以在发行完整双父凭证前剔除这对父；相同签名仍须经过原始源字段、点查与有序提交。这个请求不需要每个实例再构造一个长指令块。

真实 3mm 中，对可用数值父进行 267,175 次比较时，70,190 次需要算术求值，只有 25 次需要重新编码整数签名。按需共享得到的 220,972 份完整多父提案与预先构造每一列的版本完全一致，整轮分别为 1,932.55 和 2,092.91 ms。相同配对在 Deriche 中是 3,549.84 和 3,820.29 ms。两组程序都保留全部源 RHS。这说明 Bake 可以同时约定**计算的接口**和**第一次需要结果才物化的时间**。原生完整对照仍更快；签发数量、计算次数和整轮时间必须分别核验。[算术端口提取](../benchmarks/pass3-cell-gpu/pair-source-frontier/README.md) · [按需签名复用](../benchmarks/pass3-cell-gpu/lazy-equation-ports/README.md)

## 在两个神经父选择之间执行请求

对于 `CellSpineView8 → ExtractedExpr → TCPair`，第一份模型提案给出的 Expr 已是中间函数的完整键。Rust 可以先返回函数行及其结果端口，网络再用这个端口的学习签名选择 TCPair。编译器对每一步计算已知槽的函数依赖闭包，允许后一个独立父引用刚计算出的槽。341 个多父计划中有 64 个能据此减少独立选择数。原生试验只启用三父变两父、且中间函数有唯一物理行的子集。仍封存含三份来源的证书，原 Run 验证和提交。

3mm 在这个子集上发出 12,365 份证书，为此对初始候选先执行 613,362 次请求。可见同一模板有较低的独立选择宽度，仍可能在绝大多数候选尚未排除时过早启动请求。评价 Bake 计划时应记录每次真正签发所需的前置请求，以及请求后还有多少候选需要扫描。[静态普查与原生执行消融](../benchmarks/pass3-cell-gpu/connected-request-plans/README.md)

## 从发生变化的端口唤醒根

对“源 Cell → 完整键的函数请求 → 目标父”这段执行，后缀早于当前水位时，保留新根，再由新函数键反查它的订阅者。目标父更新也可以使旧的函数结果可用，因此还需从新目标的签名反查函数，沿函数输入找到旧根。若后缀本身足够新，单凭前三项的变化不能排除旧根。候选桶中的签名碰撞仍用完整键消解，最终恢复原始三地址证书与提交顺序。3mm 上六十多万次函数请求缩至 10,510 次，但为此从旧帧重建的订阅索引处理了 551,695 行。[逆向激活与物理父核验](../benchmarks/pass3-cell-gpu/changed-request-roots/README.md)

订阅可以跨 union 保留。以稳定事实地址订阅签名桶，再把订阅者按当前等价类分组；从上次使用到现在，只有实际变化的地址和失去代表资格的类需要更新。连续变更历史无法核验时重新构建。3mm 在 170 次跨 union 修补中，只完整建入 10,326 行并修补 10,365 个地址，独立计时的目录准备从 27.90 降到 3.18 ms。Deriche 的同一表示把完整推理从 3,488.20 降至 3,319.68 ms。按类修补能降低索引成本，仍须计入模型签发、完整核验和有序提交。[逐 Run 核验、缺失历史与独立大负载](../benchmarks/pass3-cell-gpu/incremental-request-ports/README.md)

单独训练“此次使用原路径还是反向激活”只能影响这段计算。在 3mm 的 200 次配对调用中，事后把所有正的条件收益相加为 12.75 ms。用相同的八项大小／新鲜度特征离线逐组取优，上限估计进一步降至 11.97 ms。对这个动作空间，新增权重可以改变选择分布，无法单独消除整轮超过一秒的差距。[冻结策略与同输入回报](../benchmarks/pass3-cell-gpu/request-route-policy/README.md)

## 把合并机会与放置代价一起计入回报

现在已有一条从正常运行取样的路径。编译器在成员首次入库时，按冻结 Bake 目录判断当前前缀能否继续延伸，可以给它保留单独的 backing。后面实际到达的新成员可以进入另一份 backing。两者直到原 Run 被完整组件覆盖时才成为可合并的旧 owner。dot-product 中，只保留可延伸的多成员前缀就得到 22 个不同的完整对、20 次有外部读者的提案；这一布局固定不合并时，最终图堆只多 184 B。宽放置得到 401 个完整对，固定不合并时却多 128,836 B。机会数与放置成本必须沿同一实际轨迹统计。

在 dot-product 和 stable-argmax 的 408 次自然合并上重新训练相同的九参数回归头，在留出的 GEMM-bias-ReLU 上，真实发起动作的即时净收益从 −6,344 B 变成 +8,632 B。在 gated-state 上则从 −3,896 B 变成 −1,668 B。宽放置产生的最终图堆仍分别超过普通池化 332,564 和 139,132 B。已有数据支持直接从真实源动作学习，但目前奖励只覆盖一次合并，尚未把更早放置这份 owner 的代价分摊给该决策。下一层决策应比较从第一次安置到最后退役的整段累计成本。[自然候选、部署回执与逐 Run 对照](../benchmarks/pass3-cell-gpu/prospective-owner-placement/README.md)

## 将首次放置计费到退役

逐 Run 的测量现在可以把早期放置与后期接管放回同一张账。每个源 Run 达到稳定边界时，单线程原生引擎在写时复制的子进程中销毁实际 Graph 字段，保留 Program 与观察器；父进程继续原轨迹，并在最后独立核对终点。动态 Graph 的字节·Run 是各稳定边界的存活字节之和。它按源边界计权；进程 RSS、瞬时分配峰值和累计申请则有各自的计数。

在 GEMM-bias-ReLU 的 1,652 个 Run 内，窄布局有 299 个边界比普通池化占用少，整个轨迹仍然多出 9,081,012 字节·Run。宽放置下的自然门控将其相对宽放置保留策略的累计成本降低了 1,945,852 字节·Run，但只收回先前额外驻留的 0.45%。gated-state 上相同门控又增加 759,900 字节·Run。因此，给一次后期动作归功时应保留两份反事实：先固定早期放置比较“现在是否合并”，再从首次安置处比较“是否值得为这条路径预留独立 owner”。[动态 Graph 曲线、编译库与完整来源审计](../benchmarks/pass3-cell-gpu/placement-lifetime/README.md)

## 完美的地址提案还需要多少验真

3mm 的同组诊断先记录真实在线模型选出的物理地址，再从初始状态分别重放全部地址、或只重放原验证器接受的地址。后者仍重新读取所有源前提、执行 primitive 与有序 RHS，并在 union 与 Spine 后到达相同的最终图。下列常驻推理计时不含离线捕获、初始化和最终文件导出。在线运行耗时 2,080.15 ms；只重放验真成功地址为 821.67 ms。默认 CPU 为 901.45 ms，2× 门槛为 450.72 ms。预知成功地址仍距门槛约 371 ms，后续 Bake 优先级因而应依据一个复合证书到底能消除多少次独立验证和实例组装。此处的离线地址重放不计在线发现贡献。[控制与计时](../benchmarks/pass3-cell-gpu/perfect-receipt-replay/README.md)

在独立的 3mm 分段重放中，已知成功父地址时，单是验证、组装及其余搜索部分仍需约 344 ms；原 RHS 约 294 ms，repair 约 109 ms，发布约 66 ms。逐样本扣除全部搜索后还有 474–500 ms。若继续用“一份地址元组验一次，再各自构造和提交”的接口，仅提高选择精度不能解释下一次 2×。一个可检验的替代是让编译器为同一 Run 的一批已签发实例给出共享前提、确定端口和有序效果程序。验收时同时数实际独立读取、物理分配、有效写入和跨 Run 接续；只有批内部确实不依赖中途变更的字段才可共享。

同源分叉实验把上述两个反事实拆开。dot-product 的 Run 321 只改变成员 3510／3511 的首次安置，私有存放当下少用 32 B，后续自然长到四个成员，终点却多用 64 B，并多出 47,136 个 owner 字节·Run。两个分支此前的实际 Graph 和分配器相同，之后的旧端口通过了 1,215 个边界的核验。把长程回报用于训练后，留出的 GEMM-bias-ReLU 从选择 1,364 次私有安置减至 50 次，终点额外 Graph 从 157,600 B 降到 12,560 B。该回报抑制了高代价机会，但目前普通池化仍然更小。[单动作干预、冻结权重与部署结果](../benchmarks/pass3-cell-gpu/prefix-placement-return/README.md)

## 把一页父提案编译成共享前提程序

在同一条规则的一次只读查询中，模型先密封完整父元组序列。固定一个父角色后，“地址与可见版本仍然有效”“该列等于字面量”“本行两列相同”只取决于该角色的一个源行。它们可以在页内验一次。不同角色共享变量时，等值条件仍依赖当前元组选择的两个坐标。假设后缀点查的全部动态键都从同一父角色取得，函数读取可以绑定到该父的端口；若函数输出还须等于另一个父的值，复用函数读取之后仍须独立检查这个输出条件。这给出了区分共享与逐元组工作的具体编译规则。

3mm 的 220,972 个已签发多父元组有 526,257 次实际到达的父行检查。共享后只读取 325,615 次，超出首父的复用有 112,418 次；整轮中位数却只从 1,931.27 变为 1,926.37 ms。另一组配对把含头和字典的完整凭证从 17,104,712 B 降到 5,995,652 B。两组实验共同说明模型的输出可以显著缩短，但从压缩地址得到源行、跨父比较、计算后缀、组装绑定和执行原 RHS 都仍要实际计费。[逐页共享条件](../benchmarks/pass3-cell-gpu/page-premise-programs/README.md) · [可执行后缀](../benchmarks/pass3-cell-gpu/batched-cell-verifier/README.md) · [实际发行的角色坐标](../benchmarks/pass3-cell-gpu/factored-receipt-pages/README.md)

## 从模型给出的额外信息到整波私有 Cell

union 可拆成两个可核验的问题。第一个是某条源指令到底会合并哪两个类。允许模型引用自己生成的父字、当前 Cell 的构造结果槽，以及由完整键决定的返回端口后，3mm 的 7,616 次显式有效 union 中有 7,250 个 losing root 可由已给出的提示核对。另有 20,526 次 union 来自构造器赋值或碰撞，需单独计入分母。第二个问题是哪些物理读者的哪一列需要更新。在看到反向成员之前发射 Cell、操作、版本和列掩码，3mm 的宽阈值预测命中了可寻址的 25,812 个标量位置中的 25,535 个；全部实际标量位置为 70,336 个。高局部覆盖允许提前做具体修补。当正向证据还能证明所有读者已齐，可以直接交付完整通知。独立存储实验里，仅凭模板和已有正向订阅就能省去 72,401 条显式反向边，其他外部读者仍有自己的精确来源。[端点提示](../benchmarks/pass3-cell-gpu/issuer-union-position/README.md) · [物理字段证书](../benchmarks/pass3-cell-gpu/union-location-witness/README.md) · [真实存储退役](../benchmarks/pass3-cell-gpu/implicit-owner-subscribers/README.md)

模型的输出单位也可以提高到整个 Run。3mm 的 epoch 847 有 222 条活跃规则，数量头在看到当前提案前就向 47 个模板分配了总共 7,159 个私有记录。其中规则 249 获得 2,559 个，后来发出 4,205 个父 token，并实际新建 4,205 个根。规则 122 获得 590 个，实际新建 438 个。这一 Run 共密封 15,968 个 token，再验证出 9,902 次获胜绑定和 9,082 次新根分配。提前消耗内存不影响原 Run 可见性，原始 source id 始终在合规提交点分配。

若给每一份候选都先建 Cell，3mm 全程 228,095 次新建均可使用原先的物理缓冲，但还会构造 838,045 份未发布的私有记录。若按模板而非每个猜测独占预留，同样的 232,796 个预测名额可以让 137,864 次真实分配提前完成。验证父身份与物理记录的批内复用可以同时成立：保留每一页的真实 serial 和端口，检查身份后允许尚未领用的 lane 领取同模板的空记录，记录认领位图以拒绝重复提交。最终取舍应看有效提前工作、浪费的真实分配、峰值和整轮耗时，不能用模型覆盖的 RHS 比例代替预建记录的利用率。[整波实例和时序](../benchmarks/pass3-cell-gpu/wave-cell-allocation/README.md) · [批内凭证与存储](../benchmarks/pass3-cell-gpu/group-named-cells/README.md)

## 让模型先安排一批物理 Cell

在 3mm 的 4,260 个源 Run 中，模型共封存了 845,168 份单父提案和 220,972 份多父提案。一波最多有 15,968 个候选，覆盖的不同规则最多达到 222 条。签发阶段知道父地址、页内位置、版本和模板。它可以据此决定本批次需要多少空间，以及哪些候选有权占用空间。原 Run 的验真与有序效果仍决定最终图的可见内容。

同样拿到 232,796 个物理配额，按发行顺序指派槽位有 78,955 个命中真实出生。用三个互不相同的其他程序训练八隐藏单元头，按同组配额奖励训练后命中 83,573 个，3mm 整轮由 2,001.02 增至 2,105.21 ms。已有的组凭证让同一组经过验证的获胜者领取其中任一空位，实际命中 137,864 个，达到固定规则配额的事后上界。命中率的分母应写清楚：3mm 有 228,095 次真正需要新主 Cell 的事件，最终只有 172,547 个配额能预先绑定到不同的已发行候选。对于同一接口能处理的候选，把组、引用范围和容量编码在凭证上，可以保留这种调度自由。[逐候选训练、两种种子与预算上界](../benchmarks/pass3-cell-gpu/batch-allocation-ranking/README.md)

提前分配也可以决定实际物理地址。3mm 上有 137,864 个获胜 Cell 直接在私有页中转为可读。页宽 16 时，后续 Run 的审计从这些页读取了 10,629,893 次。首槽内联可以消掉全部 232,796 次早期 fact 缓冲区申请。同布局关闭预建、开启原址预建两版的完整推理中位数分别为 1,885.21 和 1,895.90 ms。这个对照保留了早期分配的成本。跨 Run 复用较满页的空洞还能把 3mm 的终点空槽从 74,367 压到 1,346，代价是遍历已有页寻找空位。[跨 Run 的物理地址](../benchmarks/pass3-cell-gpu/resident-slab-ablation/README.md) · [首槽内联](../benchmarks/pass3-cell-gpu/inline-fact-lanes/README.md) · [空页槽复用](../benchmarks/pass3-cell-gpu/recycled-resident-slabs/README.md)

批量凭证可以缩短领取路径。Rust 为不可变页赋予本地身份，已验真的父保留该身份和槽号，领取时即可一次比较。3mm 省掉 137,864 次父的二次解码，整轮从 1,906.91 降至 1,888.07 ms，四组配对有三组更快。首次验证仍核对真实父、版本及规则条件。这也给下一种模型输出限定了范围：已有非空候选页的配额若能在同 Run 跨规则共享，3mm 的事后命中上界可以由 137,864 提到 158,785。收益依赖编译器能证明哪些页布局兼容、哪些候选可以共享空间；即使共享空间，原 Run 的可见性与有序效果仍由各自模板约束。[页与槽的领取检查](../benchmarks/pass3-cell-gpu/sealed-lane-claims/README.md) · [固定预算的可达范围](../benchmarks/pass3-cell-gpu/batch-allocation-ranking/ceilings.json)

## 让一批规则共享空间，让端口证书缩短验证

一条高阶 Cell 提案可以同时解释三个不同的决定。学习到的计数决定提前准备多少空间；编译产物给出模板的物理表示和可以共享的空槽；原规则的见证授权某个具体实例读写图。3mm 在 Run 入口预建 232,796 个私有记录，其中同规则实际领用了 137,864 个。在检查空记录的物理容量、无父引用、无已执行操作、epoch 等条件之后，模型提案还可以领取另一规则的空记录，并设置为接收方的模板。预建字节完全相同，实际命中增至 161,160 次。原规则的见证仍限制这个 Cell 能产生什么效果。池中有 7,050 次成功借用来自本轮连一个候选都没发出的规则。[跨规则物理布局与错误接收方对照](../benchmarks/pass3-cell-gpu/cross-rule-cell-pool/README.md)

模型也可以先把整波父引用封存，再根据自己刚发出的数量决定分配。一个八参数比例头用 232,068 个预建位置在共享池中服务了 189,197 次 3mm 真实新生。高分位头用 346,293 个位置服务 222,125 次。两者的实际物理采用数都达到**各自分配向量**允许的布局上界。前者的完整推理为 1,938.27 ms，后者为 1,996.38 ms，关闭预建时为 1,889.61 ms。预测物理出生的正确性与提前分配对整轮的收益是两个需要独立计量的问题。[整批预测的单规则消融](../benchmarks/pass3-cell-gpu/wave-demand-policy/README.md) · [共享池联合实测](../benchmarks/pass3-cell-gpu/sealed-wave-shared-pool/README.md)

直接影响整轮速度的是能让验证器少做多少工作。例如 Concat 的 Expr-size 计算需要两个子项的函数值。编译器已知父端口怎样构成两个完整键；任一键缺失就没有本次绑定。如果父和两个函数行的版本都早于水位，半朴素调度也不需要这一份绑定。3mm 上对这类查询的廉价检查省掉了 510,574 个单父凭证，独立原始匹配器确认每个都可以省略。模型仍运行并打分，完整推理从 1,790.01 降至 1,684.60 ms。编译器从查询结构选择这条路径，未按 Expr-size 名称分流。[端口证明、分规则统计和完整 Pass 3](../benchmarks/pass3-cell-gpu/single-pivot-certificates/README.md)

为了区分预测质量和额外购买的空间，我们还固定了原始每个 Run、每种物理布局的全部头部和 fact 缓冲区字节。3mm 使用完全相同的 232,796 个位置，按已发行数量分摊只采用了 121,807 个，沿用原分配为 137,864 个，用训练出的高分位头重新分配后为 152,991 个。这 15,127 个额外命中可以归因于空间分配得更好。代价是 3mm 推理中位数从 1,933.38 变为 1,944.82 ms。[固定物理字节消融](../benchmarks/pass3-cell-gpu/wave-budget-routing/README.md)

父引用检查还可以返回具体的已定位函数行。3mm 的正见证路径直接消费 120,889 个这样的地址和版本，验证器逐一确认原函数键、可见性及值，避免再次按键寻找行。紧凑候选队列则保留原神经序号和来源，只在验证成功时分配独立的页／槽引用。将两者接入同一推理路径后，还需重新测量组合效果：在 3mm 同一组四次测量中，过滤加紧凑队列为 1,739.79 ms，再直传正见证为 1,803.07 ms，继续预建共享池为 1,810.46 ms。数据说明每个机制确实工作，但每少一次表访问能否支付记录和验证地址的费用，取决于其余数据布局。[正见证的独立消融](../benchmarks/pass3-cell-gpu/single-scalar-handoff/README.md) · [五负载的联合消融](../benchmarks/pass3-cell-gpu/verified-wave-execution/README.md)

## 每个外部 token 到底留下多少个节点

一张凭证页可以装一万个根提案，每个父绑定仍是一个外部 token。若另有一个独立的 merge-child 决策被选中并签发，它也占一个 token。正式比较使用相同的源语义，公布三个数：归属于模型根执行的构造事实首次发布数、这些事实中最终以原始 FactRef 公开导出的数量、全部已签发根和子包数量。同一个节点即使跨了多个 Run，也只记一次。对被 union 合并的来源还应单列它的去向。到达终图前曾供后继使用的事实，仍可能有推导价值。

五个原生 Pass 3 共签发 1,775,229 个根和 7,930 个独立子包。模型根的执行共新建 340,006 个构造节点，其中 253,069 个以原来源出现在最终图。两种产出分别为每个已发包 0.191 和 0.142 个。3mm 有 119,503 个归属构造节点、92,658 个终图原来源，签发 555,566 个根和 2,508 个子包，每个包分别为 0.214 和 0.166 个。函数值、预建 Cell 以及失败提案均不增加分子。把整个初始化规则当作一个样本会掩盖常态：3mm 唯一的初始化根执行 6,709 条编译指令，构造 3,249 个节点；其余已提交根中的单根最大值为 3。[发布、最终导出和独立源核对](../benchmarks/pass3-cell-gpu/token-constructor-births/README.md)

若固定 3mm 的源 RHS 以及这 92,658 个最终原来源，要达到每个外部 token 一个有效节点，全部外部包最多为 92,658 个。当前源有 294,917 次需要保持可观察结果的 RHS 提交，相当于每个外部包平均要解释至少 3.18 次源提交。漏掉只更新函数、后来用于产生节点的 RHS 也会改变源语义。可验证的组合模板可以在保持这些提交的同时缩短外部凭证。应按实际省去的独立包计功，并单列边界验证、失效和内部待办的成本。

### Primary 与 integral 的既有对照

旧 CPU 分支已对真实 sum-bits 的 882 个 Run 做过两种退出策略。提交 `4b99d98a` 的 `benchmarks/integral-ruleset/ADOPTION.md` 记录 primary 和完整 integral 都接管 333 次 RHS、执行 359 个构造操作，各为 38.914 和 39.176 ms。提交 `229ad72e` 的 `MEMBER-VIEWS.md` 进一步验证了在原 Run 开放同一 Cell 的成员视图，两个退出策略各有 186,393 次分配请求，终点仅 10 个实例仍有跨 Run 成员。多原子迭代 Bake 的第三轮（`7ebfb9df`，`NEIGHBOR-MEMBERS.md`）拥有 24 个组合、实际切换 234 次，两个退出策略的物理分类计数仍然相同。旧程序与本次神经路径有不同的冻结源及 Run 数，其时间只在各自矩阵内比较。

图 18 的有界三阶段 GPU 对照则区分出了退出策略的真实行为。Primary 生成 3,072 个私有成员，其中 2,868 个按原槽发布；完整 integral 生成 4,764 个，其中 4,248 个按原槽发布，同时多退役了 312 个成员。把全部私有结果提前公开，384 张测试图无一通过全部观察点。因而把私有计算做早与提前让规则读到其效果需要分别验证。[图 18 的实测与错误可见性对照](../benchmarks/multi-row-generation/integral_ablation/README.md)

### 共同水位与组合验证

用默认 CPU 的独立校准固定进程增量 RSS 水位，再从原推理入口计到同一水位。3mm 的 +264.11 MiB 水位，端口路径在 1,497.23 ms 到达，加入比例预测共享池后为 1,314.86 ms。后者在该时刻实际采用约 13.1 万个私有 Cell，最终 28,149 个配额过期。sum-bits 的 +9.27 MiB 水位则是 27.29→35.41 ms。这个测量有意同时展示入口基线、自身峰值、兑现数与未兑现数，以便分辨提早完成工作和单纯提早占用空间。[新进程 OS RSS 曲线与时钟边界](../benchmarks/pass3-cell-gpu/verified-wave-rss/README.md)

新的一跳验证器用已经提交的生产者及其公开端口，在下一原始 Run 恢复完整消费输入，与当前 Spine 选出的 owner 和来源核对。sum-bits 的 1,330 次一跳接续中验证并采用 1,223 次，3mm 的 40,128 次中采用 36,855 次，后者产生 11,345 个实际新构造节点。这一阶段仍签发原始消费者 token 并执行原仲裁。若只设想全部免掉这 36,855 份根包，不多付边界凭证，3mm 的终图有效产出也只会从 0.1660 上升到 0.1778。这个数是免去这组已匹配消费者包的假设值；还可以研究一份闭包证书能否一起证明本来需要逐个发包的失败候选。验收时必须计入真实送进验证器的所有外部见证，并核对被省略的消费者是否仍在原 Run 正确发生。[当前一跳执行及错误 owner 对照](../benchmarks/pass3-cell-gpu/integral-root-certificates/README.md)

根包的收益也可以从另一端改善。3mm 保持同一编译程序、已归属的终图节点与源绑定，学习端口从一个视图增加为两个时，多父提案由 7,047,798 降至 220,972；第三个视图再省 704 个。三组均关闭只适用于多视图的特化以便配对。固定四个逻辑 row 会增加页数，但只要签发的独立绑定完全相同，产出率就不变。将移植来的策略梯度调度头从 36 参数增至 456 参数，两组都只选择一个启用局部缓存的行。要改变节点产出，这个动作空间必须能改变外部提案的内容或组合范围。[节点产出与固定 RSS 水位联合对照](../benchmarks/pass3-cell-gpu/token-yield-policy/README.md)

完整消费者组的免发已经在一个独立的未过滤构建上实测。验证器先证明整组父地址、版本与顺序均由已登记的 integral 根提供，再在原 Run 使用内部绑定，不对这组消费者发外部根包。sum-bits 实际免发 714 个包，终图原来源／外部包由 0.192324 增至 0.202666；3mm 实际免发 8,947 个包，由 0.086706 增至 0.087438。前后的终图分子及独立子包数完全一致，原始 RHS 和实际物理来源逐 Run 核验。源候选与模型分数仍被检查，这些数值只给真实省掉的线包记功。标量负证据过滤后的 0.21253／0.16603 属于另一组构建，两个改动的收益需作联合消融。[实际线包、源核对与完整分母](../benchmarks/pass3-cell-gpu/integral-packet-suppression/README.md)
